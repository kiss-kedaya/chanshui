# 服务端准备与运行约定

本文件同时用于本地运行和 `chanshui.dev` 新机部署。生产部署使用独立 systemd 服务和 nginx 反代，数据目录必须单独持久化；不要与同机其他服务共用端口或数据库。

当前部署验收：`chanshui.dev` → `<ORIGIN_IP>`（Cloudflare 橙云）→ nginx 443 → `127.0.0.1:8770`；systemd 单元为 `chanshui.service`，数据目录为 `/opt/chanshui-data`。源站不直接暴露 8770。
升级按 `docs/deploy/rolling-upgrade.md` 排空旧 Job 后切换，不直接重启中断检测。

## 最小运行结构

单Go服务 + Next.js静态目录 + SQLite文件。Linux amd64包可由 scripts/build-server.ps1 本地构建。
包内入口为chanshui，静态目录web，数据目录必须可写且跨重启保留。
运行参数示例：

    ./chanshui -addr 127.0.0.1:8770 -web ./web -db ./data/jobs.db -workers 16 -queue 128 -upstream-concurrency 64

推荐nginx等反向代理提供TLS域名，转发所有路径，保留原始Host。不要把/api请求放进SPA兜底；不要缓存/api响应。
分享URL由浏览器当前 location.origin 拼接 /history?id=<job_id>，不写死127.0.0.1、不信任用户传入的分享域名。
如需服务直接监听内网，可显式 -addr 指定对应IP；默认仍为回环。生产不要使用 -allow-private，避免用户提交内网地址。

## Job生命周期

提交 → 校验 → 生成随机128bit job_id → 事务写入queued和expires_at → 入有界队列 → worker执行 → 状态/结果落库。
job_id从提交时起就是分享ID，运行中可查看。有效期从提交起24小时，重试不续期、不换ID。
所有列表和详情查询立刻排除已到期项；每分钟按到期索引分批物理删除（每批500，单周期最多10000），积压时下一周期继续。
SQLite secure_delete开启；过期行删除不意味着磁盘文件立即变小，空页会复用。不要在线全库VACUUM。

服务重启不保存或重放API Key；未完成任务标interrupted。原题、进度和报告仍在。
每个Job创建时返回独立操作key，服务端仅保存摘要；浏览器按Job写入localStorage，刷新页面仍可用，过期或该Job全部探针完成后自动清理。该key只允许对应Job的失败项重试，不能操作其他Job，也不能读取额外报告内容；重试必须重新提供API Key。分享链接和公开Job ID始终只读，操作key不写URL、日志或报告。

## 并发边界

- 默认16个执行worker、128个等待位置，队列满立刻429+Retry-After，避免无限创建goroutine。
- 共享HTTP连接池、全局64条在途上游请求，响应体关闭才释放；每job可进一步限制并发。
- SQLite WAL、busy_timeout 5s、连接池8；持久化发生在阶段变化，不在每个SSE帧上写库。
- 完成任务约1～2分钟从内存移除，报告回SQLite查询。网络响应单次最大8MiB。
- 默认单次上游请求超时360秒；每个测试调用独立重试3次，即首次加3次、最多4次尝试，采用指数短退避；主动取消立即中止，绝不换代理。任务级总耗时预算按探针波次、并发等待和每次请求的4次尝试计算，并在报告中记录 `timing.total_ms` 与最近一次运行耗时。
- 注入与缓存分开执行。注入用两个独立短请求估计固定开销；缓存验证用三发串行、同一固定前缀。Claude提供1h显式cache_control；其他协议无完整写入字段时标unknown，不伪判通过。

本版是单服务实例、单SQLite卷的便携方案。并不支持多个独立副本共享队列；水平扩容需要外部队列/共享状态另做设计。公开大流量上线前须按服务器规格压测并在入口增加访问和滥用保护。

## 协议适配

- claude-前缀：Messages API；额外测思维链回传，展示摘要和签名。
- GPT/o系列：Responses优先；仅404/405时在现有重试预算内回退Chat，其他错误不改协议。
- Gemini/DeepSeek/Grok/GLM：OpenAI兼容Chat接口，不发送Anthropic thinking字段，不测不显示摘要/签名。不是原生Gemini SDK实现。
- 数字库17个GPT/Claude基线；其他家族仅行为参考，不强制冒充库内型号。

缓存使用同一前缀的六次串行请求。缓存可能到后续轮次才命中；确认相对首轮读取量出现增长后，按最后两轮验证衔接，上一轮读加写与末轮读相差不超过 64 token 即通过。写入字段齐全时，页面比例为 `末轮读取 ÷ 上一轮读加写`；全程仅报告读取时，比例为 `末轮读取 ÷ 末轮总输入`。缺字段时保留未知，无增长或衔接超出容差时判为未通过。注入大小不复用缓存请求，单独按两次分隔符样本估计近似值。

## 上线前仍需核对

上线前需核对域名反向代理与Host、TLS、可写数据卷、备份、资源配额、入口防滥用和依赖更新。Next.js14现有静态构建已随本版本打包；本地构建不会自动更改现网配置。

## 追加：自动同步、反馈与协议选择

默认启用后台模型库同步：启动立即检查，正常6小时、失败5分钟；固定ModelTrace官方仓库，先校验矩阵及计数，再事务缓存到runtime_state并替换只读快照。正在使用旧快照的检测不会被修改。后台日志只有同步状态，不显示密钥/联系方式；前端不显示技术同步文字。
反馈通过POST /api/feedback进入私有SQLite表，类型/长度校验、每来源每分钟5条；不信任用户伪造的转发IP。反代场景可在入口增加独立限流。无公共读取路由，包中feedback-export供管理员本机导出；联系人不进公开历史。
接口选择auto/chat/anthropic/openai；手动模式不会换协议，自适应保留现有策略。工具调用检测只验证返回结构和参数，不执行任意工具；联网通过必须有真实搜索响应块和来源，无法独立证明代理服务真实性，Chat无统一协议时unknown。

## 三请求缓存与UI运行说明

缓存三次请求串行执行：三条请求的固定前缀字节相同，不回放助手输出。第二条才加入新增段，第三条只改最后几个字。缓存率是第三轮读取除以第三轮总输入。注入点另用两个独立分隔符样本，不复用缓存前缀，也不发送缓存控制点。

缓存检测固定三个串行请求；界面展示每轮输入、输出、读、写、命中率及第三轮相对读取比例。请求默认360秒超时，每个请求独立最多重试3次，任务总耗时会在报告中显示。缓存大小会产生真实上游用量，unknown不等于失败。
前端只在任务创建、状态变化和必要的历史刷新时取数；已完成报告停止轮询，页面隐藏/离线暂停轮询，历史链接关闭自动预取，避免无意义的重复数据包。
主题/日夜在浏览器存储；模型库同步在后端运行，不需要用户刷新或复制版本号。反馈仅管理员本机导出。

## 最终UI与反馈

前端主题选择只保存在浏览器localStorage，不影响服务端。反馈写SQLite私有表，管理员用feedback-export导出；公共接口没有反馈读取路由。
